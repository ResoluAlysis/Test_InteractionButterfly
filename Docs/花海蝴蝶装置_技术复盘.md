> 目标工程：`魔菲斯 / Morpheus`（product `zaqiuLast`，Unity 2017.1.0f3 + Mono）
> AI辅助复刻工程：Unity 2022.3.62f3c1 + URP 14，`D:\UnityProject\test_00`

## 一、这是什么游戏

一个**沉浸式投影互动游戏**。观众走进探测区，脚下和身边会浮起粒子拖尾，同时几十只蝴蝶在背景上方群飞；手指划过\身体移动，沿途的蝴蝶会惊飞逃散；停住不动，蝴蝶又会慢慢聚拢过来在附近

### 三件事构成核心体验

1. **群飞**：蝴蝶(FlockChild)用 Boids 类算法自组织飞行，有分离/对齐/聚合，还有躲避
2. **跟随**：指针位置生成粒子拖尾；停住会产生"兴趣点"，蝴蝶聚拢
3. **惊扰**：指针移动会沿路径惊吓蝴蝶，让它们加速逃离

## 三、核心子系统

### 3.1 群集飞行

- 每只蝴蝶是一个 `Game_FlockChild_Test`，有自己的状态：`Flying / Playing / Resting / Escaping`
- 每帧采样邻居（半径内），算分离力、对齐力、聚合力和锚点吸引力，加权求和后积分速度
- **锚点（`Game_FlockAnchor`）** 是"这群蝴蝶想去哪"的唯一来源，由 POI 决定
- 蝴蝶数量分两批：会跟随的（20）和只做氛围的（50）

### 3.2 指针输入与粒子拖尾（重点）

这是整个项目改得最多的一块，演进过程本身就是一章...

**最终形态：**

```
后台线程：UdpClient.Receive → OSC 解析 → ConcurrentQueue.Enqueue
主线程每帧：
  消费队列 → 更新每个 id 的 (x, y, lastSeen)
  遍历所有 id：
    超时（> keepAliveSeconds）→ 移除 + 销毁它产生的 POI
    否则 → 每 spawnInterval 秒生成一个粒子（独立计时！）
```

**关键设计：**

| 设计                          | 为什么                                           |
| --------------------------- | --------------------------------------------- |
| **只信 `/set`，不信 `/alive`**   | 实测雷达的 `alive` 有 45% 的时间是空的（扫描式），但 `set` 一直在更新 |
| **`keepAliveSeconds` 容忍中断** | 触点会在数据流里"消失又出现"，不能一消失就丢弃                      |
| **每个 id 独立计时**              | 这是"多点公平"的根本——与"该点被报了几次"无关                     |
| **后台线程 + 队列**               | Unity 主线程不能阻塞在 `UdpClient.Receive` 上          |

### 3.3 兴趣点（POI）

```csharp
// 每个触点一个 PointerReport
report.active = true;
report.held   = true;      // 有触点 = "按住"
report.world  = world;
interest.Report(report);
```

`Game_FlockInterest.Report()` 内部：

1. 判断当前位置与"静止锚点"的距离是否小于 `stillRadius`
2. 是则累加 `stillTimer`，超过 `holdTime`（0.6s）就创建 POI
3. `held = true` 时 POI 有效期用 `maxHoldLifetime`（8s），每帧刷新

**触点消失时必须主动删 POI：**

```csharp
if (st.report.poiCreated && Game_FlockInterest.Instance != null)
    Game_FlockInterest.Instance.RemovePointAt(st.report.stillWorld, 3f);
```

**否则 POI 会残留 8 秒**，视觉上就是"蝴蝶聚在原地不动 8 秒"

### 3.4 栖枝点（RestSpot）

蝴蝶可以选择"停下来栖一会儿"：

- **软栖**：接近栖枝点时减速，不是硬切状态
- **容量**：每个栖枝点限 N 只
- **轮换**：栖满后过一段时间释放，避免长期被占

### 3.5 惊扰

```csharp
public void SweepExternal(Vector2 from, Vector2 to)
{
    float dist = Vector2.Distance(from, to);
    if (dist < moveThreshold) return;

    bool isJump = dist > maxSweepLength;
    Vector2 sweepFrom = isJump ? to : from;   // 跳变时退化成点检测

    SweepAt(sweepFrom, to);                   // 内层：精确扫掠
    if (_panicTimer <= 0f) { _panicTimer = panicInterval; PanicAlong(sweepFrom, to); }
}
```

**`useExternalInput` 开关**：勾上后 `Update` 直接 return，不再读鼠标——由 TUIO 组件逐触点驱动

### 3.6 配置系统

```csharp
// Game_Config：常驻单例
[DefaultExecutionOrder(-1000)] + DontDestroyOnLoad

Reload()
  → LoadSync()            重新解析 ini
  → ApplyAppSettings()    应用 [App]
  → Broadcast()           遍历所有 IConfigurable 调 ApplyConfig
  → Reloaded?.Invoke()    额外通知
```

**`IConfigurable` 是唯一契约：**

```csharp
public interface IConfigurable
{
    void ApplyConfig(Game_Config cfg);
}
```

**踩过的坑：写了 `ApplyConfig` 方法但类没 `: IConfigurable`，广播永远调不到。**（见 4.3）

### 3.7 授权系统

**离线激活码格式：**

```
GAME1.<payloadBase64>.<sigBase64>
```

- `payload` = `JsonUtility` / 手写 JSON 序列化的 `LicensePayload { fp, exp, id, ver }`
- `sig` = RSA-2048 / SHA-256 / PKCS#1，对 **payload 的原始 UTF-8 字节**签名

**关键：验证时用 Base64 还原的原始字节，不重新序列化。** 这样 Unity 端（`JsonUtility`）和 CLI 端（手写 JSON）产出的 payload 只要字节一致就能互通

**门禁三态：**

```
无授权 → 停在激活场景
校验中 → 激活 UI
通过   → 进主场景
```

## 四、技术难点与解决

按"现象 → 根因 → 解决"记录。**最有价值的是最后那一节。**

### 4.1 逆向与参考工程

#### ① 目标游戏用 Mono，可以反编译

**解决**：导出为 Unity 工程（`ExportedProject`），直接读 `Assembly-CSharp` 下的 `.cs`。这让"它到底怎么写的"从猜测变成了阅读

#### ② 加密狗相关的代码跑不起来

**现象**：`Soft_SuperDogEncriptoin/_Demo/` 里只有 demo 场景，没有 SDK DLL

**根因**：发行包裁剪掉了 SDK

**解决**：确认无需移植。自己实现了 `RSA 离线激活码 + 设备指纹`，反而更适合"交付给客户但不想联网"的场景?

#### ③ 参考工程 `Physics.Raycast` 的参数误用

```csharp
Physics.Raycast(ray, out hitInfo, ((LayerMask)(1 << LayerMask.NameToLayer("Plane"))).value)
```

**问题**：只传 3 个参数，签名是 `(ray, out hit, maxDistance, layerMask)`，所以 `(1 << 10) = 1024` 被当成了 `maxDistance`，**层过滤实际没生效**

**处理**：记录但不修复。自己的实现改用数学平面求交，避免这个副作用

### 4.2 群集行为

#### ④ 嬉戏状态的蝴蝶无法被惊吓

**现象**：正在绕圈玩的蝴蝶，划过它也不跑

**根因**：`Game_FlockPlay.Update()` 的嬉戏分支提前 `return`，从不检查 `IsEscaping`；同时 `_fleeTimer` 永远不递减，一旦设上就再也不会恢复

**解决**：`Update` 开头先检查逃跑状态；`MovePlay` 里加兜底判断；`EndPlay` 改为 public 供外部调用

#### ⑤ 嬉戏目标点抽搐、不绕圈

**现象**：蝴蝶在原地抖，或者直线冲过去而不是绕

**根因**：两个叠加——目标点用 `Random.insideUnitCircle` 每帧抖动；`drift = 0.6` 小于该速度下的最小转弯半径

**解决**：重构成独立的 `MovePlay` 移动模式，**绕圈半径必须大于转弯半径**：

```
R = speed / (damping × 1.5708)
orbitRadius = 1.6  >  R
```

### 4.3 对象池与配置热重载

#### ⑥ 热重载后新生成的蝴蝶大小不对

**现象**：改完 ini，新出现的蝴蝶还是旧尺寸

**根因**：池化实例是**快照**——`Awake`/`Start` 只在第一次创建时跑过。从池里取出来时参数还是旧的

**解决**：`SpawnOne()` 里重新应用：

```csharp
ApplyToAgent(agent, Game_Config.Instance, rerollSize: true);
```

#### ⑦ `IGamePoolable` 的多个回调只触发一个

**根因**：`GetComponent<IGamePoolable>()` 只返回第一个

**解决**：改 `GetComponents<IGamePoolable>()`，并在 `Bucket.poolableCache` 里缓存数组，避免每次 `GetComponents` 分配

#### ⑧ 多 prefab 模式下参数不生效

**根因**：`ApplyToAgents` 只改了 `agentPrefab`，而实际用的是 `prefabProvider.Pick()` 挑出来的模板

**解决**：新增 `ApplyToPrefabTemplates`，遍历 `provider.entries` 逐个应用

#### ⑨ 写了 `ApplyConfig` 却收不到热重载

**现象**：`Game_Config` 广播后打印"已应用到 0 个组件"

**根因**：**没有任何组件实现 `IConfigurable` 接口**。`Broadcast()` 的筛选条件是 `if (c is IConfigurable ic)`

**解决**：逐个加接口实现。并在 `Broadcast` 里加诊断警告，防止再次静默失败

> **这个坑踩了两次。** 第二次是 `Game_TuioPointerTrail`——方法写好了，类还是 `: MonoBehaviour`

#### ⑩ 在场粒子不跟随热重载

**问题**：池里的粒子只在"生成那一刻"读过参数，改配置后新旧混杂

**解决**：组件自己记账在场实例：

```csharp
private struct LiveParticle { public GameObject go; public Vector3 baseScale; }
private readonly List<LiveParticle> _live = new List<LiveParticle>();
```

`ApplyConfig` 末尾调 `RefreshLiveParticles()` 逐个重设缩放

**两个关键细节：**

- **池回收是 `SetActive(false)`，不是 `null`** —— 必须用 `!go.activeSelf` 判断，不能只判 `go == null`
- **基准尺寸从 prefab 资产取** —— 实例的 `localScale` 已被上次随机值覆盖，直接用它会导致尺寸漂移

#### ⑪ `maxPerPrefab` 不够导致池反复销毁重建

**现象**：粒子多的时候性能抖

**根因**：

```
触点最多 4~7 个 × 20 个/秒 × 3 秒寿命 = 240 ~ 420 个实例
```

原来 `maxPerPrefab = 256`

**解决**：提到 **1024**

### 4.4 渲染

#### ⑫ Glitch shader 重复定义 `_BlitTexture` / `sampler_LinearClamp`

**根因**：`Blit.hlsl` 已经声明过

**解决**：删掉自己那两行

#### ⑬ 加了 Renderer Feature 后画面全黑

**根因**：`renderPassEvent = AfterRenderingPostProcessing` + MSAA 未 resolve。

**解决**：改 `BeforeRenderingPostProcessing`，URP Asset 的 MSAA 设为 **Disabled**

#### ⑭ UI 背景平铺时屏幕中央出现接缝

**根因**：`tileCount` 是偶数，两张图在中心对齐

**解决**：强制 `tileCount` 为**奇数**

### 4.5 启动与流程

#### ⑮ 转场后黑屏卡死

**现象**：从 Logo 场景切主场景，黑幕不淡出

**根因**：`yield return fade.FadeIn()` 这个协程挂在**即将被销毁的 Logo 场景对象**上，加载场景时协程中断，`alpha` 停在 1。

**解决**：整体交给常驻的 `Game_ScreenFade.TransitionTo(sceneName, fadeOutDur, fadeInDur)` 一体化处理

#### ⑯ 校验场景里鼠标仍然隐藏

**根因**：`showCursor = 0` 是全局设置，激活场景需要鼠标

**解决**：`Game_Config` 加 `_cursorForceVisible` 覆盖层 + `ForceCursorVisible()` / `ReleaseCursor()`，`Game_ActivationUI` 在 `Start`/`OnDestroy` 调用（避免被 `OnApplicationFocus` 重新覆盖）

#### ⑰ 开 vSync 后帧率飞到几千

**根因**：窗口化/无边框模式下 Windows DWM 绕过了 Unity 的 vSync；旧代码 `targetFrameRate = vSyncCount > 0 ? -1 : targetFrameRate` 完全没兜底

**解决**：始终设 `targetFrameRate`，并加 `UpdateFrameCheck()`——2 秒后实测帧率，若 > `refreshRate * 1.5` 就自动回退 `vSyncCount = 0`

#### ⑱ 启动 Logo 阶段 GPU 占用 90%

**根因**：Splash 阶段 `Game_Config.Awake` 还没跑，帧率没被限制

**解决**：加 `Game_Boot`（`[RuntimeInitializeOnLoadMethod(BeforeSplashScreen)]`）提前设置；同时 `Project Settings → Quality → VSync Count = Every V Blank`

### 4.6 授权

#### ⑲ RSA 密钥文本格式

```
公钥：MODULUS|EXPONENT
私钥：8 段（P, Q, DP, DQ, InverseQ, D, ...）
```

**Key 点：验签用的是 payload 的原始字节，不重新序列化。** 否则 Unity 的 `JsonUtility` 和 CLI 手写 JSON 会因字段顺序/空白不同而验签失败

#### ⑳ `GlitchVolume.PublicKey` 未配置 → `BadSignature`

**解决**：把签发工具输出的公钥填进 `Game_License.PublicKey`

### 4.7 工具与构建

#### ㉑ `.bat` 里中文导致乱码崩溃

**现象**：

```
'censeTool' 不是内部或外部命令
'~35'
'鏌ヤ笂闈㈢殑杈撳嚭銆?'
```

**根因**：脚本是 UTF-8，但 `cmd.exe` 按系统 ANSI 代码页（GBK）解码；而且 `^` 续行符落在了乱码区

**解决**：整份脚本改**纯 ASCII、无 BOM、参数写一行，不用 `^` 续行**

> 后来写 `run.bat` 时也用 PowerShell 验证过：`非 ASCII 字节数 = 0`

#### ㉒ `WinExe` + `AttachConsole` 命令行模式完全失效

**现象**：`captured chars = 0`，文件也没生成

**解决**：`OutputType=Exe`（不是 `WinExe`）+ GUI 分支调 `FreeConsole()` 关掉双击时创建的控制台

#### ㉓ 双击 exe 闪退

**根因**：无参数时 `Main` 打印 help 就 `return 0`

**解决**：无参数直接进 WinForms GUI

### 4.8 【最重要】输入链路：同一个算法，两个游戏结果不同

这是整个项目耗时最长、最有教学价值的一段。

#### 现象

目标游戏：左右两侧都有粒子，比例大约 3:1
我们的复刻版：左侧持续生成，**右侧每秒 1~2 个甚至完全不生成**

而代码是逐行对齐的

#### 排查过程（每一步都排除一个假设）

| 假设                       | 验证方法                       | 结论                                                                                 |
| ------------------------ | -------------------------- | ---------------------------------------------------------------------------------- |
| **① 生成算法不同**             | 逐行对比 `CreateEffect` 和自己的实现 | ❌ 一致：`Distance > mouseDistance` 就生成一个                                              |
| **② `mouseDistance` 不同** | 读实际 `configFile.ini`       | ❌ 都是 `0`                                                                           |
| **③ 帧率不同**               | 解除锁帧跑到 600fps              | ❌ 右侧还是少                                                                            |
| **④ 分辨率映射不同**            | 改成 3440×1440 全屏            | ❌ 结果一样                                                                             |
| **⑤ 有隐藏的生成器**            | 用 GUID 搜遍场景所有"生成类"脚本       | ❌ 只有两个 `CreateEffect`；`LineColliderController` 是禁用状态；`EmitAtMousePosition` 场景里没有实例 |
| **⑥ 粒子参数不同**             | 读 `huaban02.prefab`        | ⚠️ 有差异（`maxNumParticles = 2`、`startLifetime = 3`），但只解释 2~4 倍，不解释"完全不生成"            |

**全部排除后，只剩一个可能：输入根本不是同一个东西...?**

#### 真正的根因

用外部工具记录**屏幕坐标**，发现：

```
左=64  右=1     ← 鼠标 98% 的帧在左侧
X范围=[1031, 1820]
```

**两个物体，但光标 98% 时间停在左边。**

继续挖平台程序（`InteractiveEngine`，一个 Unity 写的 TUIO→鼠标转换器），从 `Assembly-CSharp.dll` 里提取出这些关键符号：

```
sendmousepoints            一次发多个点
Touch_Time_Mousegap        鼠标多点触发间隔      = 10ms
Touch_Range_MoveMin        移动位置的最大间隔    = 350px
Touch_Range_SmoothMax      平滑的最大范围        = 60px
Touch_Range_StandingMax    稳定不动的最大范围    = 40px
Touch_Range_TouchMin       两个触点之间的最小间隔 = 150px
Touch_Frame_CutBefore      删除起始帧
```

**结论：**

> **Windows 只有一个鼠标光标。平台程序收到多个探测点后，必须把光标在它们之间"轮流"设置**
> **于是停留时间长的那个点生成了 98% 的粒子，停留短的只有 2%**
> **这不是算法问题，是"多点信息在单光标上被压缩"的必然结果**

**为什么目标游戏看起来均匀？** 因为它也在同样的输入下运行，只是它的总生成量更大（两个生成器 × 每个 prefab 2 个粒子 × 3 秒寿命），右侧那 2% 从"0.6 个"变成了"1.2~2 个"——**刚好越过了肉眼可见的阈值**

**所以"看起来差很多"的本质，是"卡在可见性阈值两侧"**

#### 解决：绕过平台程序，直接读 TUIO

**为什么可行：** 雷达本来就在发 TUIO（`libTUIO.dll` + 组播 `224.0.0.1:3333`）。组播允许多个程序同时收，所以可以和平台程序**并存**。

**验证（这一步是关键）：**

写了一个 `TuioProbe` 工具，直接监听 3333：

```powershell
# 绑定成功 + 加入组播成功 + 收到数据
[1] 136 字节  from 127.0.0.1:51711
    #bundle....../tuio/2Dcur.,si.alive..........4/tuio/2Dcur.,sifffff....set...
```

**能收到。于是写 Unity 端。**

#### 中间踩的坑

**㉔ TUIO 1.0 和 1.1 的格式不一样**

| 版本      | 消息形态                                            |
| ------- | ----------------------------------------------- |
| **1.0** | `/tuio/2Dcur/alive` + `,s` + ids                |
| **1.1** | `/tuio/2Dcur` + `,s...` + **`"alive"` 作为第一个参数** |

**第一版按 1.0 写，`address.EndsWith("/alive")` 永远为 false → 所有消息被丢弃 → 触点恒为 0**

**这个假数据一度误导了判断**（"雷达没数据"），浪费了好几轮。

**修正：两种都认**

```csharp
if (address.EndsWith("/alive"))     command = "alive";
else if (address.EndsWith("/set"))  command = "set";
else
{
    if (tags.Length == 0 || tags[0] != 's') return;
    command = ReadString(data, ref pos, end);   // 1.1：命令在参数里
    tags    = tags.Substring(1);
}
```

**㉕ `alive` 有 45% 的时间是空的**

修好解析后，数据是这样的：

```
[10:41:35] alive 20 条（非空 11 = 55%）  set 18 条
           id=0  set×11  存在 0.0s→1.0s
           id=1  set×6   存在 0.5s→1.0s
```

**`alive` 频繁清空，但 `set` 一直在更新，`id` 是稳定的（0,1,2,3）**

**解决：完全不信 `alive`，只信 `set` + `keepAliveSeconds` 超时**

```csharp
// 只处理 set
if (command != "set") return;

// 主线程：多久没 set 就认为消失
if (now - st.lastSeen > keepAliveSeconds) { ... }
```

**㉖ 触点消失时 POI 残留 8 秒**

**根因**：触点消失后不再调 `Report`，POI 靠 `maxHoldLifetime` 自然过期

**解决**：移除触点时主动删

```csharp
if (st.report.poiCreated && Game_FlockInterest.Instance != null)
    Game_FlockInterest.Instance.RemovePointAt(st.report.stillWorld, 3f);
```

#### 最终结果

```
[TuioTrail] 触点 2 个 | 事件 20/s | 生成 40/s | id=0(0.37,0.25)×20 | id=1(0.20,0.27)×20
```

**两个触点各 20 个/秒，完全相等。** 这是"多点公平"的直接证据

## 五、几条值得记住的结论

### 5.1 关于输入

> **多点在单光标上必然被压缩。**
> 只要中间隔着"Windows 鼠标"这一层，两个探测点就一定分不公平——这不是算法能补救的，是"一个光标"这个容器装不下两个位置

> **组播让"绕过中间层"成为可能。**
> 如果雷达是单播，平台程序独占端口，这条路就走不通，只能退回鼠标

> **量化会吃掉小信号**
> `Input.mousePosition` 是整数像素。1 像素 ≈ 0.009 世界单位，而雷达抖动量级是 0.003~0.01——**大部分帧的抖动不足 1 像素，被吃掉了**。这也是"每秒只生成 10 个"的原因（虽然当时误判为刷新率问题）

### 5.2 关于配置热重载

> **"写了 `ApplyConfig`"和"实现 `IConfigurable`"是两件事**
> 后者才是广播能找到它的凭证。这个坑踩了两次

> **池化实例是快照**
> 任何"只运行一次"的初始化（`Awake`、`Start`、一次性赋值）在池化复用下都会失效。要么每次取出时重新应用，要么记账 + 主动刷新

### 5.3 关于排查方法

> **"同一份代码、同一个环境、不同结果"这个前提，几乎总是假的**
> 一定是环境里有一项被默认成"相同"了。这次的答案是：**输入源根本不是同一个东西**。

> **排除法要排除到"能观测到的最小单位"**
> 前面五轮都在猜"算法 / 参数 / 帧率 / 分辨率"，直到把**屏幕坐标本身**记录下来，才发现光标 98% 在左边。

> **自己写的工具会骗自己?**
> TUIO 解析器按 1.0 写、对着 1.1 的数据跑，输出的"触点 0 个"看起来像"雷达没数据"，实际是解析器全丢了消息。**当工具给出反直觉的结果时，先怀疑工具**

### 5.4 关于构建

> **`.bat` 必须纯 ASCII、无 BOM。**
> `cmd.exe` 按系统 ANSI 代码页解码，UTF-8 中文会破坏语法。

> **PowerShell 不搜当前目录。**
> 必须写 `.\程序名.exe`

```cmd
run.bat                # 默认监听 3333 + 组播
```

**输出判读：**

| 输出                    | 结论                                       |
| --------------------- | ---------------------------------------- |
| `触点 1~4 个` + `id=0,1` | ✅ 标准 TUIO，Unity 端改 `port` 即可             |
| `触点 0 个` 但**包在涨**     | ⚠️ 消息类型不是 `2Dcur`（可能是 `2Dobj` / `3Dcur`） |
| `绑定失败`                | ⚠️ 端口被独占（单播），需要转发或改组播                    |
| 完全没包                  | ⚠️ 端口/组播地址不对                             |
